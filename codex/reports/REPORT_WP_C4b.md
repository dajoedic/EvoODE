## Hash Format

The Julia script implements the WP-C4a format:

```text
hash_format = sha256_raw_little_endian_float64
time_axis_order = time
state_axis_order = time_by_dimension_c_order
time and state arrays are hashed separately
```

Little-endian Float64 serialization is explicit: each `Float64` is reinterpreted as `UInt64` and
written byte-by-byte from low to high byte. This avoids relying on host memory order.

The state matrix is hashed in C-order with axes `(time, dimension)` by nested loops:

```text
for row in 1:rows
    for col in 1:cols
        append_float64_le!(bytes, values[row, col])
    end
end
```

This avoids hashing Julia's column-major matrix storage directly.

## Outputs

When Julia runs, the script writes into its own output directory:

```text
outputs/phase_c_trajectory_hashes/wp_c4b/trajectory_hashes_julia.csv
outputs/phase_c_trajectory_hashes/wp_c4b/trajectory_hash_comparison.csv
```

`trajectory_hashes_julia.csv` uses the same key and hash columns as the Python reference and also
includes shape and min/max fields:

```text
system_id
initial_condition_set
dimension
hash_format
time_axis_order
state_axis_order
time_shape
state_shape
time_min
time_max
state_min
state_max
time_sha256
state_sha256
```

The comparison classifies every compared key as one of:

```text
both_hashes_equal
time_only_equal
state_only_equal
neither_equal
missing_in_julia
missing_in_python
```

For any non-equal or missing row, the console output includes Julia and Python shape and range
fields so shape errors are visible separately from byte/hash differences. The comparison CSV keeps
the Julia and Python shape, range, and hash values side by side.

## Scope Boundary

This proves, after execution, that the same construction path under the same configuration can
reproduce the Python-side trajectory bytes. It does not prove that the already-running campaign
records consumed those exact bytes. That stronger statement would require trajectory hashes stored in
the records, which is explicitly outside WP-C4b.
